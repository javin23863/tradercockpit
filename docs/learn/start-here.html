How to judge a backtest: start here

Seven things to check in any backtest, in this order, before you believe it.

1. State the claim first

Write down what you want to learn and what result would count against it. A vague goal such as “find a good strategy” makes it easy to change the question after you see the results.

Why selection changes what a result means

2. Split build data from test data

Note which data shaped the design, the tuning, the filters or the choice of strategy. Data the strategy never saw answers a different question from data that helped build it.

In-sample and out-of-sample testing

3. Pin down every number

A metric name is not enough. Record the exact definition, the unit, the costs, the position sizing, the number of trades and the sample, so later comparisons refer to the same thing.

How to read backtest metrics together

4. Look past the one path

A backtest shows one path out of many that could have happened. Look at the drawdown, the spread of returns, the skew and the tails, and at other outcomes under assumptions you can state. This narrows the question. It does not turn a historical result into a forecast.

  • Drawdown: depth, duration and recovery.
  • Distribution shape: centre, spread, skew and tails.
  • Monte Carlo: other outcomes under a stated rule.

5. Test nearby settings

Check whether the conclusion changes with nearby parameter values, other time windows, other market regimes or other execution assumptions. A wide stable area means something different from one isolated peak.

  • Parameter robustness: a plateau or a spike.
  • Market regimes: define the state before you label it.
  • Walk-forward: move the test window through time.

6. Count what was tried

The more strategies, metrics, thresholds or variants were looked at, the more that search matters. The best of many tries is a weaker claim than a rule fixed before the test.

Selection bias and multiple testing

7. Keep a record of the test

Keep the data source, the sample, the settings, the run and the result together, so you can tell later what was tested. A complete record lets someone check the work. It does not show that the method was sound.

Keeping a record of what was tested
